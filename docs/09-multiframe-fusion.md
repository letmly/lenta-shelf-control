# 09. Multi-frame fusion: QR/штрихкод-rescue стратегия

> Документ описывает, **зачем** мы делаем фузию кадров, **что** конкретно делаем, и **почему** именно этот путь, а не super-resolution / новые сети.

---

## Зачем

Single-frame декодирование QR/штрихкода на наших видео не работает:

| Декодер | 26_12-20 (71 GT) | 43_15 (29 GT) |
|---|---|---|
| pyzbar (tight bbox) | 0 / 71 | 0 / 29 |
| pyzbar (pad +50%) | 0 / 71 | 0 / 29 |
| pyzbar (pad +100%) | 0 / 71 | 0 / 29 |
| pyzbar (full frame) | 0 / 71 | 0 / 29 |
| pyzbar (preprocessing variants) | 2 / 71 (3 %, не GT) | 0 / 29 |
| zxing-cpp (pad +50%) | 0 / 71 | 0 / 29 |
| zxing-cpp + time-window ±300 мс | 0 / 71 | 0 / 29 |

Причины single-frame провала (подтверждены глазами на сохранённых кропах):
1. **Motion blur** — робот едет, на 20 fps один кадр захватывает движение
2. **Фишай-объектив** — дисторсия по краям, QR перекошен
3. **Малый размер QR** — на 4K-видео QR-квадрат ~60-80 px, на грани декодируемости

При этом каждый ценник попадает в видео в течение **~2-5 секунд** = ~40-100 кадров.
**Идея: использовать эту избыточность для подавления шума.**

---

## Что делаем (физика подхода)

```
Кадр_1   ───┐
Кадр_2   ───┤   ECC align        Median           Decode
Кадр_3   ───┼─► (выравнивание ─► (по оси     ─►  (pyzbar
…           │   к ref-кадру)     кадров)         + zxing)
Кадр_60  ───┘
```

1. Берём GT-кадр и кроп ценника (с padding +50%) — это **template**.
2. В окне ±1500 мс (~60 кандидатных кадров при 20 fps) ищем тот же ценник:
   - `cv2.matchTemplate` — первое грубое позиционирование (находим, где ценник в кадре)
   - `cv2.findTransformECC` — субпиксельная корректировка
3. Получаем стопку из ~60 выровненных кропов одного и того же ценника.
4. **Median по оси кадров** — статистика «убивает» одиночные смазанные кадры, оставляет устойчивые модули QR.
5. На результирующем «суперкадре» — обычный pyzbar/zxing.

### Почему median, а не mean

- **Median** робастен к выбросам: если в стеке 5 кадров с motion blur и 55 нормальных, median выберет «нормальный» пиксель.
- **Mean** усреднит размытое с чётким и оставит размытое.
- **Max** — хорош для штрихкодов (тёмные полосы выделяются), но плох для QR (модули и тёмные, и светлые).

Скрипт `scripts/stacking.py` гоняет все три (`median` / `mean` / `max`) для сравнения.

## Если stacking не сработает (Plan B)

1. **Reed-Solomon module-level voting**: QR — это сетка 21×21 или 25×25 чёрно-белых модулей. После выравнивания N кадров — голосуем за каждый модуль (черно/бело) по большинству. Затем встроенная в QR коррекция ошибок (Reed-Solomon) восстановит до 30 % битов. Реализуемо через `reedsolo` (MIT) + ручная декомпозиция QR.
2. **Дообучить ESPCN super-resolution** на синтетических QR с motion blur (`pyqrcode` + случайные blur kernels). Маленькая сеть (Apache 2.0 через `basicSR`), RKNN-конвертируется. Этот путь длиннее, но даёт гарантированный буст.
3. **Fallback на текстовые поля**: если QR не читается, штрихкод как первичный ключ матчинга всё равно даёт нам шанс. EAN-13 проще декодировать после stacking, чем QR.
