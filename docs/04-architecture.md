## По компонентам

### 1. Sampling
- `cv2.VideoCapture` → читаем каждый N-й кадр (N подбираем под fps видео).
- Laplacian-variance > порог → отбраковка смазанных.
- Целевой выход: ~1–3 кадра/сек.

### 2. Детектор YOLO
- Базовая модель: **YOLOv8n** или **YOLOv11n** (Ultralytics).
- Fine-tune на bbox из размеченных CSV (это **автоматическая разметка от заказчика**, не ручная → ограничение ТЗ соблюдено).
- Один класс: `price_tag`.
- На выходе: `(x_min, y_min, x_max, y_max, conf)` для каждого кадра.

### 3. Tracker
- **ByteTrack** (есть в Ultralytics из коробки).
- Хвост трека → один track_id (= один уникальный ценник для CSV).
- Выбираем **best frame** для каждого track_id:
  - max bbox area (ценник крупнее, OCR точнее)
  - max sharpness (Laplacian variance)
  - центральнее по горизонтали (меньше перспективных искажений)

### 4. QR-декодер
- `pyzbar` (ZBar wrapper) или OpenCV `QRCodeDetector`.
- В лучшем кадре пробуем декодировать QR. Если не вышло — пробуем на 2–3 соседних кадрах того же track_id.
- Из QR парсим JSON-like структуру и **сразу заполняем 12 QR-полей**.
- **Это даёт ~40 % всех колонок «бесплатно» и почти на 100 % точно.** Это краеугольный камень нашего подхода.

### 5. Color-классификатор
- HSV-гистограмма по центральной зоне cropа.
- Правило:
  - доминирует red (H ∈ [0..10] ∪ [170..180]) → `red`
  - yellow (H ∈ [20..35]) → `yellow`
  - green (H ∈ [40..75]) → `green`
  - иначе → `white`

### 6. Template-классификатор
- На MVP — rule-based: по соотношению сторон bbox + по доминирующему цвету.
- На итерациях — лёгкая CNN (MobileNetV3 / EfficientNet-B0 nano), обучить на кропах с автоматической разметкой (по cropу и его расшифровке в GT).
- Выход: один из 7 шаблонов (см. `03-templates.md`).

### 7+8. OCR
- **PaddleOCR** (`ru`) или альтернатива **RapidOCR** (ONNX). Оба легковесные.
- Передаём кроп ценника → OCR возвращает `[text, bbox]` для каждой строки.
- Дальше **парсер шаблонов** (компонент 9) маппит OCR-боксы в нужные поля.

### 9. Парсер шаблонов
- Для каждого из 7 шаблонов — карта ROI: «вот эта область — название, вот тут цена без карты, тут цена по карте, тут штрихкод-цифрами, тут дата, тут code».
- ROI задаются в **относительных координатах ценника** (0..1).
- В каждом ROI:
  - объединяем все OCR-боксы, которые попадают в ROI
  - применяем regex для нужного типа поля:
    - цена: `r'\d+[,.]?\d{2}'`
    - дата: `r'\d{2}\.\d{2}\.\d{4}\s+\d{1,2}:\d{2}'`
    - штрихкод-цифры: `r'\d{8,14}'`
    - id_sku: `r'\d{10,12}'`
    - discount: `r'-?\d+\s*[%₽]'`
- Заполняем CSV-поля.

### 10. Aggregator
- Для каждого track_id — N OCR-результатов из best-K кадров.
- Берём по полю **самое частое значение** (majority vote) с учётом OCR-conf.
- Это сглаживает ошибки одного кадра.

## Где живёт `color` и `special_symbols`

- `color` — из компонента 5.
- `special_symbols` — отдельный мини-OCR в правом нижнем углу cropа: ищем символы `Ш`, `К`, `Л`. Если ни одного нет → `нет`.

## Метрика

`scripts/evaluate.py`:
1. Матчинг строк pred ↔ GT по IoU bbox (с учётом frame_timestamp в окне ±1 сек).
2. Для каждой матченной пары — считаем долю верно распознанных полей.
3. Ценник «зачтён», если доля ≥ 80 %.
4. Финальная метрика = доля зачтённых ценников / |GT|.

Параметры сравнения полей:
- цены, штрихкоды, id_sku — строгое равенство строки после нормализации (запятая → точка, убрать пробелы)
- product_name — fuzzy (Levenshtein normalized) ≥ 0.85
- даты — строгое равенство после нормализации
- bbox — IoU ≥ 0.5

## Что не делаем на хакатоне (вне scope)

- Свою end-to-end модель «видео → CSV». Слишком долго.
- Сложный document understanding (LayoutLMv3 и аналоги). Тяжело и не нужно при чётких шаблонах.
- TrOCR — даёт хорошее качество, но медленнее PaddleOCR. Запасной вариант, если PaddleOCR не вытянет.
